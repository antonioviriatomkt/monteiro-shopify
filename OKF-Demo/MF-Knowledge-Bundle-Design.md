# Monteiro Fabrics — Internal OKF Knowledge Bundle (Design)

A reference architecture for a **general-purpose, internal** Open Knowledge Format bundle covering everything about Monteiro Fabrics: history, brand, products, services, market, competitors, channels, content, and strategy.

This is a *design document*, not the bundle itself. Use it to build the bundle when ready, or as a reusable template for client work.

---

## 1. Core principle: one source of truth, two bundles

Do **not** merge this with the customer-facing bundle. They serve opposite audiences:

| | Internal master bundle (`mf-knowledge/`) | Public agent bundle (`/okf/`) |
|---|---|---|
| **Audience** | You + your own LLM agents | External AI assistants, crawlers, customers |
| **Contents** | Everything — including strategy, competitor intel, pricing | Sanitized facts only — products, policies, contact |
| **Tone** | Opinionated, working notes, drafts | Authoritative, customer-safe |
| **Hosting** | Private (git repo / local / Drive) | Published at `okf.monteirofabrics.com` |
| **Relationship** | **Source of truth** | **A filtered export** of the master |

The public bundle is generated by exporting every concept in the master marked `visibility: public`. Write once; publish a clean subset.

---

## 2. Type vocabulary

Keep it small and consistent. Document this list at the top of the root `index.md`.

`Company` · `Brand` · `Product` · `Range` · `Service` · `Segment` · `Competitor` · `Persona` · `Channel` · `ContentTemplate` · `Campaign` · `Objective` · `Initiative` · `Playbook` · `Reference` · `Note`

Consumers must tolerate unknown types — so you can add more later without breaking anything.

## 4. Frontmatter conventions

The spec requires only `type`. For an internal bundle, add governance fields to every concept so the bundle stays trustworthy and can be exported cleanly:

```yaml
---
type: Competitor              # required by OKF
title: Spradling
description: Global coated-fabric maker; key contract competitor.
resource: https://www.spradling.eu
visibility: internal          # internal | public  → controls public export
status: draft                 # draft | review | approved
owner: antonio
confidence: medium            # high | medium | low  (for opinion/intel)
review_by: 2026-12-01         # date this should be re-checked
tags: [competitor, coated-fabric, contract]
timestamp: 2026-06-23T10:00:00Z
---
```

Field roles:

- **`visibility`** — the export switch. The public `/okf/` bundle = every concept where `visibility: public` (products, ranges, services, company/about, contact, policies, FAQ). Everything else stays private.
- **`status`** — draft → review → approved. Lets an agent prefer approved material.
- **`confidence`** + **`review_by`** — only meaningful for the soft branches (strategy, competitors, personas, trends). They keep opinionated content from silently going stale.
- **`owner`** — accountability when the bundle has multiple contributors.

Reserved files keep their rules: `index.md` has **no frontmatter** (except the root, which may carry `okf_version: "0.1"`); `log.md` uses `YYYY-MM-DD` headings, newest first.

## 5. It's a graph, not just folders

The payoff is cross-domain links. A few examples worth wiring deliberately:

- `competitors/spradling.md` → `market/segments/marine.md`, `strategy/growth-bets.md`
- `content/templates/instagram-post.md` → `brand/voice-tone.md`, `brand/messaging-pillars.md`
- `products/collections/peel.md` → `market/trends.md`, `operations/sustainability.md`
- `customers/personas/interior-designer.md` → `market/segments/hospitality.md`, `channels/pinterest.md`
- `services/free-sampling.md` → `playbooks/respond-to-sample-request.md`

A link asserts a relationship; the prose around it says what kind. Drop one file into an LLM and it can follow the neighbours.

## 6. How to use it with an LLM

1. **Whole-bundle context** — hand an agent the entire `mf-knowledge/` folder for broad tasks (strategy memo, annual review).
2. **Subtree context** — for focused work, pass only the relevant branch: `brand/` + `content/` to write a post; `competitors/` + `products/` for a battle card.
3. **Progressive disclosure** — agents read `index.md` first, then drill into the files they need. This scales to hundreds of concepts without any embeddings/RAG setup.

The same structure is reusable for any client — it is the product you can resell.

---

## 7. Maintenance

- Update the affected concept, bump its `timestamp`, and add a line to the nearest `log.md`.
- Re-check anything past its `review_by` (mostly strategy and competitor files).
- Periodically lint: contradictions between concepts, orphan files with no inbound links, stale facts, things mentioned but lacking their own concept.
- Treat it like code: version control, review via diffs, regenerate the public export on change.

---

## 8. Conformance reminder

A bundle is OKF v0.1-conformant if every non-reserved `.md` file has parseable YAML frontmatter with a non-empty `type`, and reserved files follow their structure. All the extra fields above (`visibility`, `status`, `confidence`, etc.) are allowed — consumers must preserve unknown keys. So this internal bundle and the public export are both fully conformant.

## What's ready to auto-populate vs. needs input

| Branch | Source |
|--------|--------|
| products, ranges, attributes | **Auto** — from the live Shopify catalogue |
| services, company (contact/legal), operations/certifications | **Auto / light input** — from store data + known facts |
| brand (voice, positioning, pillars) | **Your input** — or extracted from existing site copy |
| market, competitors, trends | **Research** — web research + your knowledge |
| customers/personas, strategy, content plan | **Your input** — judgement calls, not inventable |
